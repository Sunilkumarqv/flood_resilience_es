1 Executive Summary

This project uses four distinct AI/LLM patterns, all running natively inside Snowflake with no external API calls:

RAG Retrieval-Augmented Generation

Policy PDFs are parsed, chunked, embedded, and indexed. User questions retrieve relevant chunks and feed them as context to an LLM for grounded answers.

TEXT-TO-SQL Cortex Analyst

Natural-language questions are translated into SQL using a semantic model (YAML) that defines every column's business meaning, aggregation rules, and verified query patterns.

LLM Direct LLM Generation

Structured data (comarca risk scores) is serialized as text and passed directly to llama3.1-70b for executive summaries, Q&A, and narrative insights.

AGENT Multi-Tool Agent Orchestration

A Cortex Agent routes each user question to the right tool(s) — structured SQL, document search, or both — and synthesizes a unified answer.

3 RAG Pipeline Deep-Dive

The project implements a full Retrieval-Augmented Generation (RAG) pipeline using Snowflake-native services. RAG is the pattern where an LLM's answer is grounded in retrieved documents rather than relying solely on its training data.

3.1 What is RAG and Why Use It?

For non-technical readers: Imagine asking a consultant a question. A consultant who just "knows things" might give you a confident but potentially outdated or wrong answer. A consultant who first looks up the relevant policy document and then answers — citing specific pages — is far more trustworthy. RAG is the second approach: the AI first retrieves relevant information, then generates an answer based on what it found.

RAG solves three fundamental LLM problems:

ProblemWithout RAGWith RAG
HallucinationLLM invents plausible-sounding factsLLM answers from retrieved source text
StalenessTraining data has a cutoff dateRetrieves from current documents
SpecificityGeneric knowledge, no org contextGrounded in your specific policy docs

Two PDF documents are uploaded to an encrypted internal stage. The DIRECTORY = (ENABLE = TRUE) setting allows Snowflake to list and enumerate files in the stage — required for the next step.

Stage 2: Parse — AI Document Extraction

CREATE OR REPLACE TABLE PARSED_POLICY_DOCS AS
SELECT
    RELATIVE_PATH AS FILE_NAME,
    SNOWFLAKE.CORTEX.PARSE_DOCUMENT(@FLOOD_POLICY_DOCS, RELATIVE_PATH) AS PARSED_CONTENT,
    PARSED_CONTENT:content::STRING AS FULL_TEXT,
    CURRENT_TIMESTAMP() AS PARSED_AT
FROM DIRECTORY(@FLOOD_POLICY_DOCS)
WHERE RELATIVE_PATH LIKE '%.pdf';

CORTEX.PARSE_DOCUMENT is Snowflake's built-in document intelligence function. It extracts text (and optionally layout information) from PDFs using OCR and document understanding models. The result is a JSON object with a content field containing the full extracted text.

Key design decision: Unlike external OCR tools (Textract, Document AI), PARSE_DOCUMENT runs entirely inside the Snowflake security perimeter. The PDF bytes never leave the platform. This is critical for organizations with data residency requirements.

Stage 3: Chunk — Text Segmentation

CREATE OR REPLACE TABLE POLICY_DOC_CHUNKS AS
SELECT
    FILE_NAME,
    chunk.INDEX AS CHUNK_INDEX,
    TRIM(chunk.VALUE::STRING) AS CHUNK_TEXT,
    LENGTH(TRIM(chunk.VALUE::STRING)) AS CHUNK_LENGTH
FROM PARSED_POLICY_DOCS,
    LATERAL FLATTEN(INPUT => SPLIT(FULL_TEXT, '\n\n')) AS chunk
WHERE LENGTH(TRIM(chunk.VALUE::STRING)) > 80;

Why chunk documents?

Feeding an entire 20-page document to a search engine produces poor results because the relevant information is diluted by irrelevant context. Chunking breaks the document into smaller, focused segments so the retrieval step can find the specific paragraph that answers the user's question.

Chunking strategy used in this project:

ParameterValueRationale
Split delimiter\n\n (double newline)Natural paragraph boundaries in the extracted PDF text
Minimum chunk size80 charactersFilters out headers, page numbers, and short fragments that lack semantic content
OverlapNoneParagraph-level chunks are self-contained enough for this document type
MethodSPLIT + LATERAL FLATTENPure SQL, no Python dependencies — runs at warehouse scale
Alternative chunking strategies (not used here, but worth knowing):
  • Fixed-size with overlap (e.g., 500 tokens with 50-token overlap) — better for long, unstructured documents without clear paragraph breaks
  • Recursive splitting (LangChain-style) — tries paragraph breaks first, then sentence breaks, then character counts
  • Semantic chunking — uses embeddings to find topic boundaries; more accurate but computationally expensive
The paragraph-split approach was chosen here because the policy PDFs have clear structural formatting that maps well to double-newline splits.

Stage 4: Index — Cortex Search Service

CREATE OR REPLACE CORTEX SEARCH SERVICE FLOOD_POLICY_SEARCH
  ON CHUNK_TEXT
  ATTRIBUTES FILE_NAME, CHUNK_INDEX
  WAREHOUSE = FLOOD_WH
  TARGET_LAG = '1 day'
AS (SELECT CHUNK_TEXT, FILE_NAME, CHUNK_INDEX FROM POLICY_DOC_CHUNKS);

What Cortex Search does under the hood:

  1. Vector Embedding: Each chunk is converted to a high-dimensional vector (embedding) that captures its semantic meaning. "River flood protection" and "fluvial mitigation infrastructure" produce similar vectors even though the words are different.
  2. BM25 Index: A traditional keyword index is also created for exact-match queries. Cortex Search uses hybrid retrieval — combining semantic similarity with keyword matching — for the best of both worlds.
  3. Auto-refresh: TARGET_LAG = '1 day' means if the source table changes (new documents added, chunks updated), the index rebuilds within 24 hours automatically.

Stage 5: Retrieve & Generate

When a user asks the Cortex Agent a policy question, the flow is:

  1. The Agent routes the question to the search_policy_docs tool
  2. Cortex Search retrieves the top-k most relevant chunks
  3. The chunks are injected into the LLM prompt as context
  4. The LLM generates an answer grounded in the retrieved text

5.3 Verified Queries (VQRs)

Verified queries are pre-approved question/SQL pairs that anchor Cortex Analyst's responses. When a user asks something similar to a VQR, the analyst can match it with high confidence instead of generating SQL from scratch.

NameQuestion PatternWhat It Queries
most_vulnerable_comarcas"Which comarcas have the highest composite flood vulnerability score?"Top 10 by AVG_COMPOSITE_SCORE with risk/SVI/loss breakdown
buildings_in_flood_zones"How many buildings are in high-risk flood zones by comarca?"BUILDINGS_IN_SFHA, TOTAL_BUILDINGS, PCT_IN_SFHA per comarca
critical_infra_at_risk"How many hospitals and schools are in flood zones?"Counts by CLASS (hospital, school, fire_station, etc.) with % in high-risk
high_svi_flood_overlap"Which comarcas have both high social vulnerability and high flood exposure?"Comarcas where SVI ≥ 0.6 AND PCT_IN_SFHA ≥ 30%
total_annual_loss"What is the total expected annual loss region-wide?"SUM of losses across all 34 comarcas

6.3 Agent-Mediated Generation (Cortex Agent)

Inside the Cortex Agent, the LLM is used at multiple stages:

  1. Orchestration: The LLM reads the user question and decides which tool(s) to invoke
  2. Text-to-SQL (Cortex Analyst): An LLM generates SQL from the question + semantic model
  3. RAG synthesis: After document chunks are retrieved, an LLM generates the final answer
  4. Response composition: If both tools were used, an LLM merges structured results + document findings into a coherent response
Model comparison — CORTEX.COMPLETE vs Cortex Agent:
  • CORTEX.COMPLETE is a single LLM call — you provide the full prompt and get one response. Simple, fast, but limited to what fits in the prompt.
  • The Cortex Agent is a multi-step orchestration — the LLM is called multiple times: once to route, once per tool, once to synthesize. More powerful, but uses more tokens and time.

8 Data Security & Governance

Data Never Leaves Snowflake

All AI processing — PARSE_DOCUMENT, CORTEX.COMPLETE, Cortex Search, Cortex Analyst — runs inside Snowflake's infrastructure. No data is sent to external APIs (OpenAI, Anthropic, etc.).

Encryption at Rest

All stages use ENCRYPTION = (TYPE = 'SNOWFLAKE_SSE') — Snowflake-managed server-side encryption. PDFs, CSVs, and the semantic model YAML are encrypted at rest.

RBAC-Governed Access

The Cortex Agent, Streamlit dashboard, and all tables are subject to Snowflake's role-based access control. Only authorized roles can query the data or invoke the agent.

Semantic Model as Governance

The semantic model acts as a governance layer — it defines which columns are exposed, how they should be aggregated, and what questions are valid. The agent cannot query columns not defined in the model.

9 Glossary

TermDefinition
RAGRetrieval-Augmented Generation. An AI pattern where an LLM's answer is grounded in retrieved documents rather than relying solely on training data. Reduces hallucination and enables current/specific answers.
ChunkingThe process of splitting documents into smaller, semantically meaningful segments (chunks) for indexing and retrieval. This project uses paragraph-level splitting (double-newline delimiter).
Vector EmbeddingA numerical representation (array of floats) that captures the semantic meaning of text. Similar meanings produce similar vectors, enabling semantic search. Created automatically by Cortex Search.
BM25A traditional keyword-matching ranking algorithm. Cortex Search combines BM25 with vector search for hybrid retrieval.
Cortex PARSE_DOCUMENTSnowflake's built-in AI function for extracting text from PDFs (and other document types) using OCR and document understanding models. Runs entirely inside Snowflake.
Cortex Search ServiceA managed Snowflake service that creates and maintains a hybrid (vector + keyword) search index over text data. Supports auto-refresh via TARGET_LAG.
Cortex COMPLETESnowflake's function for calling LLMs (e.g., llama3.1-70b) directly in SQL. Accepts a prompt string and returns generated text. Runs inside Snowflake, no external API calls.
Cortex AnalystSnowflake's text-to-SQL service. Given a natural-language question and a semantic model, it generates and executes SQL. Powered by LLMs + the semantic model's verified queries.
Cortex AgentAn AI agent defined in Snowflake that can orchestrate multiple tools (Cortex Analyst, Cortex Search, etc.) to answer complex questions. Uses LLM-based routing to decide which tools to invoke.
Semantic ModelA structured, machine-readable description of what database columns mean — their business definitions, aggregation rules, and relationships. Powers Cortex Analyst's text-to-SQL accuracy.
Verified Query (VQR)A pre-approved question/SQL pair in the semantic model. Anchors Cortex Analyst's responses: when a user question matches a VQR pattern, the analyst uses the verified SQL with high confidence.
Apache OssieAn open, vendor-neutral interchange format for semantic models. Incubating at the Apache Software Foundation. Supports richer ai_context documentation including instructions, synonyms, and examples.
Semantic ViewA native Snowflake SQL object (CREATE SEMANTIC VIEW) that stores semantic model metadata as a first-class database object.
DANADepresion Aislada en Niveles Altos — a cold-drop atmospheric phenomenon specific to the Iberian Peninsula that produces sudden, catastrophic flash flooding.
PATRICOVAValencia's regional flood-risk zoning plan classifying areas into zones A1 (highest risk), A2, B, and C (lowest risk).
H3Uber's Hexagonal Hierarchical Spatial Index. Divides the Earth's surface into hexagonal cells at various resolutions. Used here for efficient geospatial joins.
Dynamic TableA Snowflake table that automatically refreshes when its source data changes, within a specified TARGET_LAG. Used here for the alert pipeline.
