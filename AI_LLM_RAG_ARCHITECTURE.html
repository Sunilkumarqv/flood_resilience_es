1 Executive Summary

This project uses four distinct AI/LLM patterns, all running natively inside Snowflake with no external API calls:

RAG Retrieval-Augmented Generation

Policy PDFs are parsed, chunked, embedded, and indexed. User questions retrieve relevant chunks and feed them as context to an LLM for grounded answers.

TEXT-TO-SQL Cortex Analyst

Natural-language questions are translated into SQL using a semantic model (YAML) that defines every column's business meaning, aggregation rules, and verified query patterns.

LLM Direct LLM Generation

Structured data (comarca risk scores) is serialized as text and passed directly to llama3.1-70b for executive summaries, Q&A, and narrative insights.

AGENT Multi-Tool Agent Orchestration

A Cortex Agent routes each user question to the right tool(s) — structured SQL, document search, or both — and synthesizes a unified answer.

2 End-to-End Architecture Overview

Data flows left-to-right: from raw sources, through processing and indexing, into the AI layer, and out to users.

3 RAG Pipeline Deep-Dive

The project implements a full Retrieval-Augmented Generation (RAG) pipeline using Snowflake-native services.

For non-technical readers: RAG is like a consultant who first looks up the relevant policy document and then answers — citing specific pages — rather than relying on memory alone. The AI first retrieves relevant information, then generates an answer grounded in what it found.
ProblemWithout RAGWith RAG
HallucinationLLM invents plausible-sounding factsLLM answers from retrieved source text
StalenessTraining data has a cutoff dateRetrieves from current documents

3.1 The Five-Stage RAG Pipeline

Stage 1: Ingest — Upload PDFs to Snowflake

CREATE OR REPLACE STAGE FLOOD_POLICY_DOCS
  DIRECTORY = (ENABLE = TRUE)
  ENCRYPTION = (TYPE = 'SNOWFLAKE_SSE');

COPY FILES INTO @FLOOD_POLICY_DOCS/
FROM 'snow://workspace/...'
FILES=('data/policy_docs/Valencia_Flood_Mitigation_Plan_2024_Intro.pdf',
       'data/policy_docs/Valencia_Flood_Mitigation_Plan_2024_Strategies.pdf');

Two PDF documents uploaded to an encrypted internal stage.

Stage 2: Parse — AI Document Extraction

CREATE OR REPLACE TABLE PARSED_POLICY_DOCS AS
SELECT
    RELATIVE_PATH AS FILE_NAME,
    SNOWFLAKE.CORTEX.PARSE_DOCUMENT(@FLOOD_POLICY_DOCS, RELATIVE_PATH) AS PARSED_CONTENT,
    PARSED_CONTENT:content::STRING AS FULL_TEXT
FROM DIRECTORY(@FLOOD_POLICY_DOCS) WHERE RELATIVE_PATH LIKE '%.pdf';

CORTEX.PARSE_DOCUMENT extracts text from PDFs using OCR and document understanding models, entirely inside Snowflake.

Stage 3: Chunk — Text Segmentation

CREATE OR REPLACE TABLE POLICY_DOC_CHUNKS AS
SELECT FILE_NAME, chunk.INDEX AS CHUNK_INDEX,
    TRIM(chunk.VALUE::STRING) AS CHUNK_TEXT,
    LENGTH(TRIM(chunk.VALUE::STRING)) AS CHUNK_LENGTH
FROM PARSED_POLICY_DOCS,
    LATERAL FLATTEN(INPUT => SPLIT(FULL_TEXT, '\n\n')) AS chunk
WHERE LENGTH(TRIM(chunk.VALUE::STRING)) > 80;
ParameterValueRationale
Split delimiter\n\n (double newline)Natural paragraph boundaries
Min chunk size80 charactersFilters headers, page numbers
OverlapNoneParagraphs are self-contained
MethodSPLIT + LATERAL FLATTENPure SQL, no Python needed
Other chunking strategies (not used here): Fixed-size with overlap (500 tokens + 50 overlap), recursive splitting (LangChain-style), semantic chunking (embedding-based topic detection). Paragraph-split was chosen because these PDFs have clear structural formatting.

Stage 4: Index — Cortex Search Service

CREATE OR REPLACE CORTEX SEARCH SERVICE FLOOD_POLICY_SEARCH
  ON CHUNK_TEXT
  ATTRIBUTES FILE_NAME, CHUNK_INDEX
  WAREHOUSE = FLOOD_WH
  TARGET_LAG = '1 day'
AS (SELECT CHUNK_TEXT, FILE_NAME, CHUNK_INDEX FROM POLICY_DOC_CHUNKS);

Creates both vector embeddings (semantic similarity) and a BM25 keyword index. Uses hybrid retrieval for best results. Auto-refreshes within 24 hours when source data changes.

Stage 5: Retrieve & Generate

SELECT PARSE_JSON(SNOWFLAKE.CORTEX.SEARCH_PREVIEW(
    'FLOOD_ANALYTICS.FLOOD.FLOOD_POLICY_SEARCH',
    '{"query": "What projects are planned for the Xuquer river?",
      "columns": ["CHUNK_TEXT","FILE_NAME"], "limit": 3}'
)) AS SEARCH_RESULTS;

6.2 Executive Summary (Notebook Lab 5)

Same CORTEX.COMPLETE call but with a different persona prompt: "You are a senior flood risk analyst for Valencia Emergency Management. Write a 3-paragraph executive summary." Converts tabular data into a professional narrative.

6.3 Agent-Mediated Generation

Inside the Cortex Agent, the LLM is invoked at four points:

  1. Orchestration: Read the question, decide which tool(s) to invoke
  2. Text-to-SQL: Generate SQL from question + semantic model
  3. RAG synthesis: Generate answer from retrieved document chunks
  4. Response composition: Merge structured results + document findings
CORTEX.COMPLETE vs Cortex Agent: COMPLETE is a single LLM call (fast, simple, limited to prompt contents). The Agent is multi-step orchestration (multiple LLM calls: route → tool → synthesize). More powerful, more tokens.

8 Data Security & Governance

Data Never Leaves Snowflake

All AI processing runs inside Snowflake. No data sent to OpenAI, Anthropic, or any external API.

Encryption at Rest

All stages use SNOWFLAKE_SSE. PDFs, CSVs, and YAML are encrypted at rest.

RBAC-Governed Access

Agent, dashboard, and tables are subject to Snowflake role-based access control.

Semantic Model as Governance

The semantic model defines which columns are exposed and how they aggregate. The agent cannot query undefined columns.
